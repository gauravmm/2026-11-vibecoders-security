# AI tool and agent security for startups

Research snapshot: 2 November 2026

This note covers two related but distinct activities: **using third-party AI SaaS** (including coding assistants and connected copilots), and **building AI features or agents** into a product. SaaS procurement and configuration controls do not replace secure product engineering; conversely, a product security program does not establish whether an employee may paste customer data into a consumer chatbot.

## Executive findings

1. Treat model context as a mixed-trust input stream. User instructions, retrieved documents, email, code comments, issues, webpages, tool metadata, and tool results can all carry hostile instructions. Prompt injection is a system-level risk; prompt wording or a classifier alone cannot establish an authorization boundary.
2. Reduce the consequence of a model mistake. Give agents narrow, short-lived, task-scoped identities and tools; isolate execution; limit egress; separate read from write; and make destructive or external actions require explicit, informed approval enforced by ordinary application code.
3. Treat connectors as privileged integrations. Inventory them, vet their source and update path, scope credentials per connector, inspect tool schemas, pin versions where possible, and log actions. An approved server or connector may still surface attacker-controlled content or change behavior.
4. SaaS data protection is feature-, account-, and contract-specific. Verify the actual plan, terms, retention, training use, connected-data boundary, telemetry, subprocessors, admin controls, and incident commitments. “Not used to train foundation models” does not mean “not stored,” “not processed,” “not visible to tenant admins,” or “safe from prompt injection.”
5. Coding agents need the same controls as developers with shell, repository, cloud, and production access. Keep them away from production secrets and production data; use disposable workspaces, least-privilege tokens, backups, reviewed diffs, protected branches, and normal CI/security gates.
6. Evaluate the whole system continuously: model, prompt, retrieval, connectors, permissions, runtime, and user interface. Test realistic indirect-injection and data-exfiltration paths after model, prompt, tool, or policy changes. Record residual failures and block release on high-impact paths.

## Threat model and practical boundaries

Prompt injection is a confused-deputy problem: the model may mistake attacker-controlled data for instructions, then use legitimate authority held by the application or user. This can happen without a malicious model or compromised connector. An attacker may place instructions in a public issue, email, document, webpage, image, or tool description; a user asks for an ordinary summary or coding task; and the agent uses a trusted read/write connector to cross a data boundary. Output filtering and “ignore instructions in documents” help in some cases but do not reliably create that boundary. Enforce authorization, data scope, and allowed side effects outside the model.

| Situation | Primary security question | Baseline boundary |
|---|---|---|
| Employee uses AI SaaS | What data and account authority leave the company boundary? | Approved business account and terms; classified-data policy; SSO/MFA; admin controls; connector review; minimal context; retention and audit review. |
| Coding assistant in IDE/CI | What can untrusted repository content cause the agent to read, execute, change, or send? | Disposable isolated workspace; no production credentials; scoped repo token; constrained network; approval for shell/network/write; reviewed PR and normal CI. |
| Product uses model without tools | Can input, output, retrieval, or logging leak or corrupt sensitive data? | Data minimization; tenant isolation; output validation; access-controlled retrieval; abuse/cost limits; privacy and retention controls. |
| Product agent uses tools | Can untrusted context induce a privileged or irreversible action? | Server-side policy checks for every call; per-action identity and authorization; least privilege; confirmation bound to exact action/arguments; sandbox, egress limits, audit and recovery. |

## SaaS adoption checklist

- Prefer a centrally managed business/API plan with SSO, MFA, admin controls, auditability, contract terms, and clear data retention. Consumer accounts are not equivalent even when the interface and model name match.
- Check contractual language and current admin configuration for model training, feedback, telemetry, retention, human review, deletion, and connected services. A “no training” commitment is only one part of the decision.
- Classify data before use. Remove identifiers and secrets when the task does not require them; use synthetic examples for debugging; do not assume that pasting less context only affects quality rather than exposure.
- Apply existing identity and data-access hygiene before enabling workplace copilots. They can make already-overbroad file permissions easier to query and summarize. Fix oversharing and stale access first.
- Manage browser extensions, IDE extensions, plugins, custom GPTs/agents, MCP servers, and OAuth apps as software and identity integrations. Review permission scopes and where their tokens/data go.
- Establish a rapid offboarding path: disable the service/connector, revoke tokens, preserve logs, and assess which data was exposed if a prompt-injection or credential incident occurs.

## Building AI features: engineering baseline

1. **Threat model flows, not only prompts.** Map each source, trust level, model context boundary, retrieval index, tool, identity, destination, and side effect. Include cross-tenant and cross-user paths.
2. **Keep authorization deterministic.** The model may propose an action; application policy independently authorizes the authenticated actor, object, and exact action. Never rely on a system prompt to hide data or enforce access control.
3. **Separate untrusted content from control data.** Label provenance; structure context; avoid concatenating secrets into prompts; minimize retrieved content; filter and normalize inputs where useful. These measures can reduce attacks but do not eliminate injection.
4. **Harden retrieval.** Apply ACL filters before retrieval and re-check after retrieval. Prevent poisoned or stale documents from overriding tenant policy. Track source IDs and changes; provide deletion propagation; test index isolation and metadata filters.
5. **Use constrained interfaces.** Prefer narrow typed tools over general-purpose shell/browser access. Validate schemas and destinations; enforce quotas; require idempotency/replay protection; maintain allowlists and deny lists in code/config, not model memory.
6. **Design recovery.** Use reversible operations, checkpoints, backups, transaction boundaries, dry runs, and rollback. A model can make an unwanted change without an attacker, so availability and data-integrity controls matter too.
7. **Manage model and data supply chain.** Inventory model/provider/version, weights/adapters, datasets, prompts, packages, embeddings, and evaluation sets. Verify provenance/integrity; scan dependencies; review data rights and poisoning exposure; control model upgrades and fallback routes.
8. **Bound availability and cost.** Limit tokens, retries, tool calls, fan-out, concurrency, and per-user spend; detect loops and abuse; define safe fallback and circuit breakers.
9. **Monitor drift and incidents.** Track refusal/attack outcomes, anomalous tool calls, sensitive retrieval, and spend. Re-run evaluations when model behavior, prompts, tools, data, or deployment settings change.

## Automated red-team practice

Use an approved framework such as [Promptfoo](https://www.promptfoo.dev/docs/red-team/configuration/) for application-level adversarial test generation/evaluation, and/or [Microsoft PyRIT](https://microsoft.github.io/PyRIT/latest/code/framework/) for composable multi-turn attack workflows. [NVIDIA garak](https://github.com/NVIDIA/garak) provides a broad probe/detector scanner useful for model and endpoint checks. Select based on the application and team skill; none substitutes for an application-specific threat model or human testing.

### Safe test setup

- Target a dedicated staging deployment with the same policy code, retrieval/connector wiring, and permission checks as production. Use synthetic users and seeded canary records, never real customer data or production secrets.
- Give the test agent a throwaway identity with only staging access. Point all email, webhooks, and outbound tool destinations to controlled sinks; block public egress by default. Disable or simulate payments, deletion, publication, deployments, and other irreversible actions.
- Separate attack-generation and target credentials. Store them in CI secrets, grant only staging scope, cap spend/concurrency/time, and revoke on job completion. Keep payload/result artifacts access-controlled and time-limited.
- Pin scanner versions and record target/model version, prompt and tool-manifest hashes, test corpus version, run ID, and configuration. Re-run a small deterministic regression set on each relevant change; schedule broader generated campaigns and human-led tests periodically.

### Test cases and release gate

| Test path | Example controlled setup | Pass condition |
|---|---|---|
| Direct and indirect injection | User message plus hostile text in seeded document, issue, email, web page, image/OCR text, or tool result; include hidden/encoded and multilingual variants where relevant. | Agent may summarize hostile content, but does not treat it as authority, call unrelated tools, or reveal protected data. |
| Data exfiltration | Seed a fake canary secret in one allowed record; inject requests to email it, add it to a public PR, include it in a URL, or send it through a webhook/search query. Route attempted egress to controlled sink. | No canary crosses the intended boundary; blocked tool calls and authorization denials are visible in logs. |
| Authorization boundary | Two synthetic users/tenants/repos with deliberately distinct documents and tool scopes; ask for a different user's records, another repo, or broader action through direct and indirect injection. | Zero cross-user/tenant/repository disclosure or action. Enforce in backend policy and assert from tool traces, not only the final text. |
| Dangerous action and approval | Seed a fake delete/deploy/refund/send action; try to induce it through prompt, retrieved content, or tool metadata; alter parameters after approval and attempt replay. | No consequential action without approval for the exact arguments; changed/replayed requests are denied. Prefer a non-executing mock. |
| Output handling | Feed model strings resembling HTML/JS, SQL, shell, URLs, file paths, tool arguments, and malformed JSON into downstream paths. | Values are schema-validated and safely encoded/parameterized; no generated command runs just because it was emitted. |
| Resource exhaustion | Repeated/recursive tasks, oversized context, tool fan-out, retries, and expensive queries under safe load caps. | Per-user and per-task limits stop loops and keep cost/latency within configured budget. |

For high-impact cases, gate on **zero confirmed critical/high-severity leaks, unauthorized actions, or cross-tenant accesses**; a high aggregate pass rate does not offset a single severe failure. Require deterministic authorization tests to pass on every run. Triage scanner-only failures with a human, preserve successful attacks as regression cases, and require an explicit risk owner to accept any remaining high-severity issue. Repeat probabilistic probes several times and track rates rather than treating one clean sample as proof. Do not test against production or grant the scanner real-world write authority.

Keep the suite useful rather than brittle: block on confirmed severe outcomes and deterministic policy assertions; report lower-severity or uncertain model-judge findings for review. This avoids making subjective wording scores a noisy release blocker while retaining strict gates for real data and side effects.

## Source interpretation and limits

The cited incidents are demonstrations, disclosures, or reported operational failures, not estimates of how often attacks occur. Vendor documentation describes intended product behavior and contractual scope, not independent validation. Frameworks and checklists are starting points; startup teams should prioritize controls according to the data, identity, action authority, and recovery cost in their actual deployment. Security testing should include normal application threats as well as AI-specific paths.
